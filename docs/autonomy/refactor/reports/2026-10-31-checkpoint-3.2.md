## 1. Summary

Three hand-kept classifications said what a node was: the folder its header sat in (`source/`, `filter/`, or `core/` for the envelopes and the modulators), the `SourceCategory` each of fifty-nine node classes reported through a virtual `category()`, and the editor's create menu, about seventy-five entries written out by hand twice (once for the canvas's create menu, once for the node context menu's Replace-with). They disagreed: the folder put `vibrato.h` under `filter/` and `shaper_source.h` under `source/`; the categories called the evolution holders Combiners or Generators and the wavetable an Oscillator; the menu had its own idea of both. The target (section 3.2) asks for one: "each type declares its family once, where it is registered; folder, colour and the create menu all follow from it."

Now each registration carries a `TypeTag` — `{.family = Family::Noise, .label = "Red"}` — and the registry is the one place that knows a type's family, its menu label and its shelf. `Family` is ten values in Part 3 section 3's order (Oscillators, Noise, Wavetable, Additive, Physical, Filters, Envelopes, Modulators, Combiners, Utility); `Shelf` is `Main` or `Experimental`; `registered_types()` answers in registration order and `types_in(family, shelf)` is what a menu draws. Eighty-five registrations: sixty-three on the main shelf, twenty-two Experimental — today's Experimental sub-menu plus the eight types no menu listed at all (NameGate, StaticVar, StaticRange, the `KSPianoString` loading alias, Biquad, BowTable, Mesh2D, PierceFilter), which Matt put there in one sentence rather than classify them now. Twenty-seven registrations carry a `.label` (twenty-six at Task 1; the review wave added Pierce Filter's), each one where the menu's label differs from what `derived_label()` makes of the type name ("Red" for `RedNoiseSource`, "BW Lowpass" for `BWLowpassFilter`); the other fifty-eight derive theirs, and a test refuses a label that equals its derivation. `SourceCategory`, `Component::category()` and the fifty-nine overrides are gone, with the tests' own node; nothing at run time asks a node object what family it is in — the editor and the CLI ask the registry by type name, as they already did for everything else.

The editor's menus are generated. One loop, `shelf_menus(Shelf)`, walks `kFamilyOrder`, asks `types_in` for each family on the shelf, draws a sub-menu per non-empty family with the registry's labels, and puts one separator before the fifth family (the sound-making families above the line, the shaping ones below — the one presentation fact that is not in the registry). The create menu and Replace-with both call it; the Experimental sub-menu is the same loop over the other shelf. The four-entry quick block (Curve, Envelope, Var, Range) stays hand-written, as the plan's ruling 16 says: it is a convenience, not a classification. The registrations file was regrouped so that registration order is menu order, family by family, main shelf then Experimental, a banner per group; a test pins every family's list in order, so a registration added in the wrong place fails the build's tests, not Matt's eyes.

Node colours follow the family through a `Theme` (`tools/mforce_ui/theme.h`): one colour per family, one each for the editor's own nodes (output, parameter, note, curve, unknown), the dynamic-pin gold and the strip views' envelope trace, with built-in defaults equal to the literals they replace. `node_title_color` asks the theme and the registry's family and nothing else — the two name-matching helpers (`is_noise_type`, `is_wavetable_type`) and the switch over categories are gone. Because colour follows family, **seven types changed colour**: `HybridKSSource` teal→tan (Wavetable), `PierceFilter` lavender→teal (Physical), `DistortedSource` and `Shaper` teal→lavender (Filters), `Vibrato` teal→pale gold and `SegmentSource` reddish-orange→pale gold (Envelopes; Segment had been coloured as a noise by the deleted name-matching helper), `Wormhole` teal→grey (Utility). The colour change and the helpers' deletion landed in the registry commit `67071f8`, not in the Theme commit, since the family switch that replaced the helpers made them unreferenced (section 10, lesson 4). Loading a theme from JSON and the editor's other fifty-odd colour literals are Part 7's.

Forty-two headers moved by `git mv` into one folder per family under `engine/include/mforce/source/` — `oscillator/`, `noise/`, `wavetable/`, `physical/`, `filter/`, `envelope/`, `modulator/`, `combiner/`, `utility/`, beside the `additive/` that was already there. `engine/include/mforce/filter/` is gone: `filter` was never a dependency boundary (an FM oscillator used a filter, vibrato used a noise source), and the module map now says so — the `filter` module is deleted and every `may_include` list drops it. The node headers that lived in `core/` (`envelope.h`, `envelope_presets.h`, `envelope_json.h`, `var_source.h`, `range_source.h`, `curve_node.h`, `name_gate.h`, `multi_source.h`) are nodes, not contract, and joined their families; `core` keeps the contract and its own two sources (`ConstantSource`, `TapSource`, in `dsp_value_source.h`). The `.cpp` files stay in `engine/src/`.

## 6. Decisions and rejected alternatives

The sixteen planning rulings (plan Ledger 1–16) and the execution rulings, in the order made. Each says what it costs if wrong.

**Planning.**

1. **The registry entry is the one classification; the per-node `category()` is deleted.** A virtual on every node is a second declaration that drifted (the holders said Combiner or Generator for what the table calls Wavetable). Nothing at run time asks a node object for its family. Cost if wrong: a node in hand without its registry name cannot say its family; no such caller exists.
2. **A `TypeTag` struct with designated initializers**, not more positional parameters on `register_type`: `{.family = Family::Noise, .shelf = Shelf::Experimental}` reads at the registration; a fourth and fifth positional argument would not. `label` and `shelf` default so the common registration names only its family.
3. **Labels: today's where today has one, derived otherwise.** The menu must read as today — a byte-identity analogue for the editor; the eight unlisted types take the derived form, whose rule is one function with a test. An override is kept only where it differs from the derivation. Cost: twenty-seven `.label` strings a reader might think redundant; a test refuses one that is.
4. **The Experimental shelf is a registration fact, binary.** Matt's 2026-08-26 grouping becomes `Shelf::Experimental` on the type; the generated menu mirrors the families under it; today's "(none yet)" placeholders go, an empty family is not drawn. Everything not in today's main menus is on that shelf (Matt, 2026-10-31), including the `KSPianoString` alias, which 3.5 deletes.
5. **Registration order is menu order.** The alternative, an `order` field on the tag, is a second thing to keep in step; moving the registration blocks once into family order costs a script and nothing after. Every sweep over `registered_types()` is order-free (checked: the split, the configurator, the audit, the part set). Cost if wrong: a registration appended at the bottom of the file lands at the bottom of its family's menu — and fails `run_menu_content_tests` until the table says so too.
6. **`Family` is ten values with a parallel name table** (`family_name`), display names plural where the table says so ("Oscillators", "Filters"), enum names singular. `kFamilyOrder` is Part 3 section 3's order and the menu's.
7. **Colours follow the family, so a type whose family changed changes colour.** Keeping per-type colour overrides to preserve today's picture would be the third hand classification by another name. Seven changed (section 1); REVIEW R9 names them.
8. **`Theme` holds the node colours and the editor's five special-node colours and nothing else in this checkpoint.** The other fifty-odd literals and the JSON loading are Part 7's, where the editor is rebuilt. Cost if wrong: Part 7 moves the rest into a struct that already has the shape.
9. **The menu's one separator (between Additive and Physical) is kept** as the one presentation fact not in the registry. Cost: one line in the editor.
10. **Folders last, by `git mv`, with no file renamed or split.** The moves carry no behaviour and land after every behaviour-bearing task is green, so a build break has one cause. Splitting the multi-type headers is 3.6's.
11. **The `.cpp` files stay in `engine/src/`.** The classification the target asks for is the header's folder; the module map lists the `.cpp`s by name. 3.6 may revisit.
12. **`ConstantSource` and `TapSource` stay in `core`.** They are the contract's own, not nodes a user creates; the registry does not list them.
13. **The envelope headers leave `core`**, with `var`, `range`, `curve`, `name_gate` and `multi`: `core` is the contract and the registry, and these are nodes. `render` includes `source/` already, so `instrument.h`'s include of the envelope is no new direction.
14. **A/B set, base and scope as 3.1's**: library + baselines, the old arm from the build at `f1f8244`, 0 DIFFER expected.
15. **Order of tasks**: the registry first, then the menu (the first reader), then the colours (the second), then the folders (no reader), then the close.

## 10. C++ lessons

### Lesson 1: designated initializers, the object initializer you already know

`reg.register_type("RedNoiseSource", {.family = Family::Noise, .label = "Red"}, …)` builds a `TypeTag` naming the members it sets, in declaration order, and leaves the rest at their defaults (`label = nullptr`, `shelf = Shelf::Main`). This is C++20's designated initialization, and it is the C# object initializer — `new TypeTag { Family = Family.Noise, Label = "Red" }` — with two differences that matter. First, the names must come in the order the struct declares them (`{.shelf = …, .family = …}` is an error), because C++ initializes members in declaration order and refuses to let the text suggest otherwise. Second, it works only for an *aggregate*: a struct with no user-written constructor, no private members, no virtual functions — a plain bag of data, which is exactly what a tag should be. The alternative the plan rejected, `register_type(name, Family::Noise, "Red", Shelf::Main, …)`, is the positional call every C# author has learned to distrust: the fourth argument is a string and the fifth an enum, and a reader at the call site has to know which is which. The struct gives the call its words.

Why `const char* label` and not `std::string`: a `TypeTag` is built from literals at registration; a `const char*` to a string literal is valid for the whole program (literals have static storage), costs nothing to copy, and keeps the struct an aggregate — `{.family = …, .label = "Red"}` needs that. The pointer is the C# reader's trap, though: a `const char*` is an address, not a string, and a tag built from a temporary `std::string`'s `.c_str()` would point at memory the temporary frees. So the registry does not keep the caller's pointer. At registration it copies the label's text into its own `std::string` inside the entry and points the stored tag at that copy, which lives as long as the registry (an `unordered_map` node does not move when the map grows). The queries return `std::string` for the same reason: a value the caller owns, not a pointer into someone else's storage. The rule to take away: a `const char*` in a struct is fine when the struct is a message passed in and copied out of; it is a liability the moment the struct is stored.

### Lesson 2: `enum class` and the parallel name table

`enum class Family { Oscillator, Noise, … }` is a *scoped* enumeration: its values are `Family::Noise`, never bare `Noise`, and they do not convert to `int` by themselves (you write `int(f)` or `static_cast<int>(f)` when you index an array with one, as `theme().family[int(reg.family(name))]` does). That is what C# enums always were; C++'s older plain `enum` leaks its names into the enclosing scope and converts to `int` silently, which is why the codebase uses `enum class` throughout. What C++ does not have is C#'s `Enum.ToString()` or `[Description]` attributes: an enum carries no names at run time. So the names live in a parallel table — `family_name(Family)` is a `switch` (or an array indexed by `int(f)`) returning `"Oscillators"`, `"Noise"`, … — and the enum and the table are two things that must agree. The checkpoint pins that agreement in a test (`kFamilyTable`'s rows name the display string for every type) rather than with a macro that generates both from one list, which is the other common answer and is harder to read. `kFamilyOrder` is a third parallel: an array of the ten values in menu order. Today it equals the declaration order, and section 7 lists that as debt; it exists so that the menu's order is a thing with a name rather than an accident of the enum's text.

The reason to prefer an enum over the strings themselves ("Noise" as a `std::string` on the tag): a misspelt string compiles and fails at run time; a misspelt `Family::Nois` does not compile. The registry's `types_in(Family, Shelf)` and `theme().family[int(f)]` both want a small dense integer, not a string compare.

### Lesson 3: `git mv`, and what history keeps

Forty-two headers changed address and nothing else, by `git mv old new` and a commit. Git does not store renames: a commit is a tree of blobs, and `git mv` is `mv` plus `git rm --cached old` plus `git add new`. What Git does is *detect* renames when it shows a diff — `git diff -M` and `git log --follow` look for a deleted path and an added path whose contents are similar (above 50 percent by default) and present them as one rename. The moved headers' contents changed by one or two include lines each, so every one of the forty-two is detected as a rename (`git diff -M 1f087cb caac81c --stat` lists them as `{old => new}`), `git log --follow engine/include/mforce/source/envelope/envelope.h` walks back through `core/envelope.h`, and `git blame` (with `-M` and `-C`, which the project's `blame` alias sets) attributes each line to the commit that wrote it, not to the move. Two consequences for the refactor's rules. Git holds the full history (CLAUDE.md), so no header carries a "moved from core/ on 2026-10-31" comment. And a move should travel in a commit of its own, as this one did: if the move and an edit to the moved file land together, rename detection has less to match on and `--follow` can lose the thread — which is why the plan put the folders last, after every behaviour-bearing edit was committed.

### Lesson 4 (short): a `static` function nobody calls is the compiler's business

Deleting the name-matching colour helpers (`is_noise_type`, `is_wavetable_type`) could not wait for the Theme task: once Task 0's family switch replaced their only callers, each became a `static` free function with no caller in its translation unit, and MSVC reports that as C4505 ("unreferenced function with internal linkage has been removed") at the `/W4` the engine builds with. In C#, an unused private method is an analyzer hint at most. In C++ a `static` free function has *internal linkage* — it is visible in this `.cpp` only — so the compiler alone can see that nothing names it, and says so. The project is not warning-free (the music headers and the UI's `fopen` calls carry a dozen pre-existing ones, none from this checkpoint) and does not build with `/WX`; the refactor's rule is to add none. That is why ruling 18 moved the deletion a task earlier than the plan said: the plan's task boundary was not a warning-clean state, and a step that leaves one is a step that leaves a mess for the next.
