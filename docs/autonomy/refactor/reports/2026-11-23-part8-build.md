## 2. The shape

```
engine/
```

   Without it the compiler would refuse a forbidden include only in a

## 9. Lessons

### 9.1 An include folder is the classpath, and a target is who gets it

C# and Java find a type through a project or module reference: no
reference, no type, and the compiler says so. C++ has no such thing in
the language. `#include "mforce/music/structure.h"` is a file name, and
the compiler looks for it in a list of folders it was handed on the
command line. Whoever controls that list controls what code can reach.

Before Part 8 every engine file was compiled with one folder,
`engine/include`, so every header could be found from anywhere and the
module rules lived in a script that ran afterwards. Now each module has
its own `include/` folder, and CMake hands a file only the folders of its
own module and of the modules its `USES` names:

```cmake
target_include_directories(mforce_render PUBLIC  engine/render/include)
target_link_libraries(mforce_render      PUBLIC  mforce_core mforce_source mforce_patch mforce_contract)
```

`PUBLIC` is the word that matters. It means "my own files need this, and
so does anyone who uses me", because my headers include theirs. `PRIVATE`
means "only my own files" (the warning flags are private: a module's
strictness is not its users' business). `INTERFACE` means "only my users"
and is what a module with no `.cpp` has, since it compiles nothing
itself. The C# analogue of `PUBLIC` is a project reference that flows to
whoever references you; of `PRIVATE`, `PrivateAssets="all"`.

The limit follows from the same rule. Play uses perform, perform's
headers include voicing's, so play must be handed voicing's folder or
perform's headers would not compile inside it. A direct include of
voicing from play therefore compiles, and the meter is what refuses it.

### 9.2 A header is not compiled until something includes it

In C# every `.cs` file in a project is compiled, always. A C++ header is
not a unit of compilation. Only `.cpp` files are compiled; a header is
text pasted into whichever `.cpp` includes it, and is checked then, with
that `.cpp`'s folders and flags. A header nothing includes is never
checked at all, and a header included only from another module's `.cpp`
is checked with the wrong module's folders.

Most of this engine is headers: voicing, contract and util have no
`.cpp`, and source has five for about ninety headers. So "the compiler
refuses a forbidden include" would have been true only where a module's
own `.cpp` happened to include the offending header. The header check
closes that: for each module CMake writes one small `.cpp` that includes
every header of the module, and compiles it with the module's own
folders and warning flags. It is built as an *object library*, a target
that compiles its files and makes nothing from them, because the point
is the compile, not the output.

### 9.3 Why `CHECK` is a macro

```cpp
#define CHECK(cond) ::mforce::testing::check(static_cast<bool>(cond), __FILE__, __LINE__, #cond)
```

A failed check should print where it is and what it tested. A C++
function cannot see its caller's file, line or the source text of its
argument. A macro can, because it is expanded as text at the place it is
written: `__FILE__` and `__LINE__` become that place, and `#cond` turns
the argument's source into a string. C# gets the same from compiler
attributes on parameters (`[CallerFilePath]`, `[CallerLineNumber]`,
`[CallerArgumentExpression]`); C++20 has `std::source_location` for the
first two and nothing for the third. So the macro is one line that
gathers those three and calls an ordinary function, which does the
counting and printing. `REQUIRE` adds one thing: on failure it throws a
small type that `run_tests` catches, which is how a test ends at the
failed line without `return` codes threaded through every helper.
