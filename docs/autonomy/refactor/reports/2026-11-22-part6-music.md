## 6. Decisions the session made

Three were corrections to the signed design, written into its section 14
before any code:

1. **The kit has two members and the codecs stand beside it.** The design
   put `SettingsCodecs` inside `ComposeKit`. That would have made
   `compose`'s header include JSON. One registration call still fills
   both.
2. **`Composition` has no `warnings` list.** Nothing in `compose` would
   write to it once unknown names are errors.
3. **The four file readers are declared without JSON and defined in
   `.cpp` files**, where the design said `_json.h` headers that
   strategies would then have included.

The rest, in the order they came up:

4. The module is named `shelved`, not `compose_shelved`: the meter maps
   an include to a module by its folder name.
5. Voicing, compose and perform each include `core` for the random
   source, as the model does. The design's table left it out.
6. An unknown name is refused when the template is READ, where the file
   names it, and at compose where code set it. The design said only "an
   error".
7. The five strategies that cannot work without settings fail when given
   none. The design said `settings_of` gives defaults; it does, and these
   five check first.
8. A strategy with nothing to set has the shared type `NoSettings`. It
   lives in `voicing/` because a voicing selector and a compose strategy
   both name it and voicing is the lower module.
9. `realize_phrase` (about 85 lines) and `setup_piece_` moved whole.
10. `play`'s own sum of a piece's beats goes through the one rule for a
    section's start, and `--play` realizes a piece that has passages and
    no events. Neither was in the brief.
11. The six duplicated blocks the meter gained at step 3 are the strategy
    headers' class preambles (includes, the name, the settings alias).
    Left as they are.
12. `corpus/mtd_seg/engine_passage_strategies.py` wrote four old keys,

13. The default passage (the review's Major, section 8) is fixed in this

## 9. C++ lessons

### 9.1 A `const` method: a promise about the object, checked by the compiler

```cpp
virtual Passage compose_passage(Locus, const PassageTemplate&) const = 0;
//                                                             ^^^^^
```

The trailing `const` says the method does not change the object it is
called on. Inside it every member is read-only, and a `const` reference
to the object can call only `const` methods. C# has this for a `readonly
struct` and nothing for a class; Java has nothing. Here it turns a
sentence in a comment ("strategies are stateless") into something that
fails the build: `compose` takes `const ComposeKit&`, the registries hand
out `const PassageStrategy&`, and a strategy that tried to remember
something in a member would not compile. The alternative was a test,
which checks the strategies that exist; `const` checks the ones not
written yet. One hole: a `static` variable inside a function is not a
member, so `const` does not see it. Three of those remain (section 7).

### 9.2 Why two headers cannot include each other

C# has no headers: two classes in one assembly refer to each other
freely, because the compiler sees every class before it compiles any
body. C++ reads a file top to bottom, and `#include` is paste. If
`a.h` includes `b.h` and `b.h` includes `a.h`, the guard (`#pragma once`)
stops the second paste, so one of the two is read before the other's
class exists. Step 4 made it work by placing each include after its own
class and before its bodies, which is fragile: move a line and it stops
compiling, for a reason that is nowhere near the line.

The cycle was real before the split and hidden by it: both classes were
declared in one file and their bodies written in another. The fix is the
usual one. What both need (`degree_in_scale`, `choose_shape`) lives in a
third header that depends on neither class, and each class header
includes that. The C# analogue is two assemblies that reference each
other: the cure is the same, a third assembly both depend on.
