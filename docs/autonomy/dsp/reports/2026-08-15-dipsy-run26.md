## Front C — backlog 3k: audio-thread race audit  [2f7bbba]
The item asked for a proper audit of what audio_callback can hold across
graph mutations. Findings, ranked by likelihood of being the 08-06 AV:
1. **g_bufferPlayback is a raw pointer INTO g_outputWaveform** — and four
   sites (render_waveforms, both transport renders, the Generate-pending
   clear) resized/cleared that vector with no lock and no stop. A
   reallocation mid-playback = audio thread reading freed memory. The
   header comment literally claimed buffer playback "owns its data
   (member buffer)" — the false belief was documented at the bug site.
   Fixed: buffer_playback_detach() (under the audio lock) precedes every
   mutation of that vector.
2. **Graph rewiring raced the stream taps.** update_node_dsp /
   update_all_dsp reassign live DSP shared_ptr edges; g_streamSource /
   g_streamChannels dereference those same objects per sample. A link
   edit or pin change during streaming was a torn pointer read. Fixed:
   both now hold g_audioMutex (split into _unlocked internals to avoid
   recursive locking).
3. **Properties config edits** call set_config directly — which can
   rebuild ExplicitPartials' internal arrays while a stream tap is
   mid-next() on the object. Fixed: locked.
Already safe: the load/new graph swap (guarded since run 23) and voices
(each owns its InstrumentPatch). Residual noted in the backlog: the
Envelope stage-editor and Curves-tab breakpoint edits still mutate live
objects unlocked — same fix pattern if a crash ever names them.
Deadlock scan of every call site: clean.
