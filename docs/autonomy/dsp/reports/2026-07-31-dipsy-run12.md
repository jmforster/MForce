## Front 1 — additive hot loop, 1.2-1.6x (item 8 stage 2, G4) — LANDED

Spec: `docs/superpowers/specs/2026-07-31-additive-hot-loop-design.md`.
Commit `aafbe9b`.

### Stage 2a — bit-exact

Four changes, none of which alter the math:

- **`IPartials::sum_partials()`** — one virtual call per *sample* instead of
  one per *partial*. The accumulator is threaded in/out rather than each
  implementer returning a subtotal, so a nested `MultiPartials` sums in the
  same order as one flat loop (float addition isn't associative; subtotalling
  would have moved the last bits). `MultiPartials` also stops re-scanning its
  set list once per partial index.
- **Per-sample scalar cache** — the eight envelope `current()` reads and the
  scalars derived from them were being fetched once *per partial*. At 96
  partials that is 768 virtual calls per sample to read eight numbers that are
  identical for all of them. Now refreshed once in `partials_next()`.
- **Per-partial cache** for `pmult` / `rolloff` / motion-scale, keyed on
  `(multE, roE)` by exact float compare. `pow()` is deterministic so a reused
  value is bit-identical to a recomputed one; with constant `multEnv`/`roEnv`
  — every patch in the repo — that is one rebuild per note and zero `pow()`
  calls per sample.
- **`fmod(x,1)` -> `x - truncf(x)`** — exact for this argument range, one
  instruction against a libm call.

Verification: `tools/null_test_additive.py`, 14 patches chosen to hit
FullPartials, ExplicitPartials, motion/shimmer/trade/onset, bandwidth,
formant+floor, gliding FormantSequence, the expand rule, paramMap curves, and
the instrument pre-render path. **14/14 byte-identical.**

### Stage 2b — fast sin

Measured before building anything: rendering the ladder with the `sin` call
deleted outright gave 2.15x where stage 2a alone gave 1.30x, so `sinf` was
~40% of what remained. Replaced with an exact quarter-turn fold plus a
degree-9 odd minimax polynomial in turns (`engine/include/mforce/core/fast_math.h`).

Not bit-exact, so it is measured rather than asserted
(`tools/residual_test_additive.py`): across all 14 patches the **worst
deviation is 1 LSB at 16 bit**, residual RMS -125 to -140 dBFS. In float32
arithmetic the polynomial's max error is 2.2e-7 against
`std::sin(x*TAU)`'s own 6.0e-7 — it is *more* accurate than the call it
replaces, because the old path paid rounding forming `x*TAU` in float. No
toggle, per the no-back-compat rule.

## Front 2 — FM "modulate everything" (item 7 stage 2, G3) — LANDED

Commit `f34e395`. Your goal 3, verbatim: *"Modulate literally everything and
see what happens!"*

FMSource's six params are all ValueSources, so `carrierRatio` and `modRatio`
— the parameters a fixed-architecture FM synth structurally cannot reach —
are modulatable. 24 curated patches over that space, 9 of them deliberate
rule-breakers:

- **tier 1 (10)** one param at a time, sub-audio and audio rate: ratios driven
  at audio rate, phase driven at audio rate (PM stacked on FM), frequency on
  red noise, amplitude at audio rate (ring-mod over FM).
- **tier 2 (5)** several/all at once — incommensurate LFOs, all-noise wander,
  both ratios at audio rate, ratios counter-swept through unison, and an
  oversampled dense case.
- **tier 3 (9)** ultrasonic carrier, `modRatio` swept *through zero and
  negative*, irrational ratio pairs, a modulator running faster than its own
  carrier, an FMSource driving another FM's depth, index-60 aliased/oversampled
  pair, triple-nested pitch modulation, velvet-noise phase jumps.

All 24 render with sound. Wiring verified mechanically rather than assumed —
`tools/fm_matrix_spectra.py` shows spectral-centroid standard deviation
spanning 99 to 2719 Hz across the batch, so every modulator is reaching its
param. (This mattered: a silently-unwired param would still have produced a
perfectly good FM tone and sailed through the novelty rank.) RMS is
near-constant across the batch, which is correct — FM is amplitude-preserving.

Novelty-ranked against the conventional library plus this batch's own
textbook-FM control. Which of these is *musical* is yours to say — queued, not
guessed.

### Side finding: the oversample default question has a wrong premise

`research/fm_alias/measure_patch.py` generalises the alias measurement to any
FM patch. Every previous alias number (runs 8 and 11) was taken at a **high
carrier** (C7/C8). The open policy question — "oversample 4-8 for
bright/high-index FM?" — conflates high frequency with high index. Measured:

```
ultrasonic carrier   M=1/2/4/8 ->  0 / 2.7 / 5.7 / 12.5 dB   monotonic, converging
index 60 @ 220 Hz    M=1/2/4/8 ->  0 / -0.0 / -2.4 / -2.3 dB  NOT converging
```

At ±31.8 kHz deviation from a 220 Hz carrier, M=16 isn't a limit at all —
oversampling there doesn't clean the sound, it *changes* it. So a blanket
"oversample for high index" is wrong in that corner; the rule that survives
measurement keys on carrier frequency and total deviation against Nyquist, not
on index.

## Front 3 — where the remaining time goes (item 8 stage 2c direction)

`tools/ablate_additive.py` stubs one stage of the partial body at a time,
rebuilds, and reports marginal ns/sample/partial:

| variant | marginal ns |
|---|---|
| full | 57.3 |
| no_sin (polynomial replaced by passthrough) | 29.0 |
| loads_only (two array loads and a multiply) | 3.3 |

Two things follow. The polynomial sin is still half the loop. And the
**memory-bound floor for the current data layout is 3.3 ns** — a 17x headroom
over where we are. That is the number that justifies stage 2c: the gap is not
explainable by arithmetic count, so the next investment is a restructured,
explicitly vectorized inner loop (SoA batches of 4-8 partials, several partial
sums to break the serial accumulate chain), not more scalar micro-optimization.

Spec for the next stage: `docs/superpowers/specs/2026-07-31-additive-simd-soa-design.md`.

### Two anti-results, both measured

**Branchless sin is not faster.**

I thought the folded polynomial's two quadrant selects were mispredicting, so
I fitted a degree-13 odd polynomial over the full half-period that needs no
folding at all — one more FMA, zero branches, and I verified it was accurate
enough (-123.4 dB in float32, the same class as the `std::sin(x*TAU)` it would
replace at -124.5 dB).

Controlled A/B says it is **a wash** (200p render 1024.9 vs 1020.5 ms). MSVC
was already compiling the selects branchlessly. Rejected and reverted: the
folded degree-9 version stays, because it is the more accurate of the two
(-133.3 dB vs -123.4 dB) at equal speed.

**The 4x unroll is slower.** The per-partial body is one long dependency chain
(pmult -> pfreq -> cutoff -> phase -> sin -> amplitude), so unrolling 4x with
four independent accumulators should have given the scheduler work to
interleave and removed the one loop-carried dependency. Fifteen lines, no SIMD.
Controlled A/B: **0.88x / 0.94x / 0.93x** on the 32/96/200-partial ladder,
neutral elsewhere. Reverted.

Both of these are worth the space because of what they jointly rule out. The
remaining 57 ns is not the accumulator chain, not branch misprediction, and not
instruction-level-parallelism starvation — the compiler was already handling
all three. There is no scheduling trick left. Anything that moves this number
has to be real vector arithmetic, which makes stage 2d a genuinely bigger
investment than it looked this morning, and worth weighing against stage 2e
rather than assuming.

The spec reflects that: phase 1 is now an isolated SIMD prototype on synthetic
arrays with an explicit **2x abort criterion** — if vectorization can't beat
scalar by 2x with no engine structure in the way, stop and write down the
number rather than starting a refactor.
