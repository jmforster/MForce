### Soprano E / I / U — why they fail, measured rather than swept

You called these three unsatisfactory and said the pass overall was
diminishing returns, so no new 43-WAV batch. Two measurements instead.

**1. Vowel separability collapses with pitch** (`research/vowel/
harmonic_sampling.py`, RMS dB distance between harmonic patterns over the
run-23 grid):

| voice | f0 | mean vowel-pair distance | E-vs-I |
|---|---|---|---|
| Bass | 110 | 26.94 dB | 24.21 dB |
| Tenor | 165 | 23.87 dB | 18.88 dB |
| Alto | 220 | 21.39 dB | 12.01 dB |
| **Soprano** | **440** | **14.80 dB** | **10.71 dB** |

Monotonic, and the mechanism is explicit rather than inferred: at 440 Hz
soprano E and soprano I put **F1 on the same harmonic (h1) and F2 on the same
harmonic (h5)**. They can then differ only in gain, never in pattern — which
is precisely "all sound like I". F2 has to move ≥220 Hz at soprano pitch
before the peak harmonic changes at all, against 55 Hz for a bass. Harmonics
below 3 kHz, where identity lives: 27 / 18 / 13 / **6**. Soprano O and U each
have exactly **one** harmonic in the F1 band and one in F2 — two samples of
the whole envelope, which is "lacks vowel character" stated numerically
(U-vs-O measured 5.20 dB, the closest pair in the entire grid).

**2. But the recipes were still giving away ~7 dB** (`pitch_vs_recipe.py`, a
2×2 crossing recipe with pitch):

| E/I distance | f0 = 220 | f0 = 440 |
|---|---|---|
| alto formant recipe | 27.05 dB | **16.90 dB** |
| soprano formant recipe | 18.45 dB | **10.20 dB** |

Both recipes lose 8–10 dB to the octave — that is the comb, and no recipe
fixes it. But the alto formants, left where they are and simply sung at A4,
keep 16.90 dB.

**A bug in my own harness, caught by its own guard.** The first run of this
2×2 reported the soprano recipe at 10.20 dB at *both* pitches — identical to
two decimals, which is not a thing that happens. These patches drive pitch
from `score[].note` through `instrument.paramMap.frequency`, so setting
`src.frequency` does nothing and the retune had silently not happened. The
script now reads the fundamental back out of each render (comparing energy on
the k·f0 comb against the half-offset comb, which a suppressed h1 cannot
fool) and refuses to score an arm that did not retune.

**Why this is not `e3_altoXpose`**, which you heard as a pennywhistle: that
variant scaled the alto formants up ×2 *along with* the pitch. Formants are a
property of the vocal tract, not of the note — a singer's tract does not
shrink when she goes up an octave, so scaling them is physically wrong and
sounds it. Here the formants do not move at all; only the note does.

bigger number means the vowels are more different from each other, not that
any one of them is the vowel it is supposed to be. REVIEW 25.

**But nothing called it.** Neither `iowa_reference.py` nor `score_candidate.py`

done and steps 4–5 were not. The smoke numbers were still riding the k·f0 mask.

Wired it: opt-in on `piano_mf`, B measured per note and passed to
`harmonic_env` / `broadband_ratios` / `motion_stats`, `b_map()` carrying it to
the candidate side (the reference's B, per spec item 4).

**Then the naive wiring regressed the bass** — C2 band2 3.995 → 29.34, and C2
is an eval note. Diagnosed instead of guessed (`diag_stretch_bass.py`): the
fitted B is not wrong, the *fixed* `tol_frac*f0` mask is. Model position error
against the real tracked peaks, in mask half-widths:

| note | n 1–16 | n 17–32 | n 33–64 | n 65–90 |
|---|---|---|---|---|
| C2 | ≤0.15 | up to 5.0 | up to 9.9 | up to 6.0 |
| C4 | ≤1.20 | up to 10.5 | up to 8.4 | — |
| C5 | up to 1.3 | up to 6.1 | up to 6.0 | — |

A single stiff-string B holds to n≈16 and not above. Keeping every tracked
partial inside a model-centred mask would need a half-width of 0.36–0.63·f0,
six to ten times the current one — which would swallow the very gaps the
metric exists to measure.

So the fix is a better **centre**, not a wider mask: `rm.measured_lines()`
masks on the peaks the tracker actually found (exact by construction), falling

in the reference so the candidate is masked on the reference's lines.

## Front D — 3e-NEXT(b3): the bass motion numbers were beating, not broadening

Commit `bcf3413`. Taken because front B's own output flagged it and it is
Python-only, so the comp lane could not block it.

Front B left C1/F1/C2 reporting `resid_cents_rms` of 181–469 cents against
5–15 c from G2 up. A tritone of "line broadening" is not a measurement.

Isolating one partial needs its neighbours — one spacing (~f0) away — outside
the heterodyne passband, i.e. `lp < f0/2`. The stock `LP_HZ = 40` violates
that below f0 = 80 Hz, and the break sits exactly between C2 (f0/2 = 32.7) and
G2 (49.0), which is exactly where the numbers broke. So the residual on those
notes was **adjacent-partial beating**.

Confirmed with a sensitivity sweep (`diag_lowf0_heterodyne.py`) — the same
control run 18 used on beat rate: a real measurement holds still as the cutoff
moves, an artifact tracks it. Across cutoffs 40/30/20 Hz, C1 swings 318.7 →
11.2 c, a **28.5× sensitivity**, against 1.45–2.0× for every note from G2 up.

**The sweep also killed the obvious fix.** A purely spacing-relative cutoff
(`lp = frac*f0`) wrecks the treble: at C6 that is a 419 Hz passband and
resid_cents goes 6.1 → 37.3 c. The rule has to be a **cap**, not a scale —
`lp = min(LP_HZ, 0.4*f0)`, which does not bind above f0 = 100 Hz. Tap count
scales only when the cutoff narrows (firwin(1025) has a ~43 Hz transition band
at 44.1 kHz, so a narrowed cutoff at fixed length would be meaningless) and
stays exactly 1025 otherwise, so nothing above the cap moves by a bit.

    resid_cents_rms   C1 468.70 -> 4.27   F1 340.44 -> 21.45   C2 181.45 -> 4.66
                      G2/C3/C4/G4/C5/C6 unchanged to the digit

C1's `amp_frac` also falls 42% → 12% — the beating was inflating that too.

Scorer, same patch, C2 being an eval note: **term2 1.3114 → 0.8123, TOTAL
1.0449 → 0.9202.** Taking the session as a whole, the same untouched
`patches/piano1/template.json` went **1.1879 → 0.9202** — 22.5% of the
objective was measurement artifact rather than patch quality. That matters
directly for the gated 600-eval run: it was going to be searching against it.

Regression: viola and clarinet references byte-identical (their f0s are all
above the cap); the piano reference *file* is byte-identical too, since it
stores no per-note motion — the fix moves what the scorer computes for
candidates, which is where it counts. Both test suites still ALL PASS.

**Not fixed, and not claimed:** F1 stays unstable — 6.4× sensitivity at
21.45 c. Far better than 340 but not a number I would rely on. That is two
attempts on the low-f0 family this run, so per the 2-attempt rule it is
annotated on the backlog rather than tried a third time; the likely cause is
window length, not the filter (F1's 1.0 s sustain gives 1 Hz resolution
against a 43.7 Hz spacing).
