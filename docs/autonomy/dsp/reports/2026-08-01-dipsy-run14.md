# DSP run 14 — Dipsy — 2026-08-01 (scheduled)

Three fronts, all build/metric, no blind taste iteration. Headline: the
additive loop got 1.6x on everything and another 1.7x on top of that for
every motion-bearing patch, and both wins came from the same bug class —
a libm call sitting in the per-partial per-sample body.

The CMA-ES eval patch (`v6_05_cmaes_best`) went **16.1 s → 8.9 s (1.81x)**
across the session. That is the item-3d blocker, by name.

## Front 1 — item 8 stage 2d phase 1: the isolated SIMD prototype

Per the stage-2d spec, phase 1 is a throwaway benchmark over synthetic arrays
with a hard 2x abort criterion, written BEFORE touching `Partials` — two
theories had already died there and a prototype is far cheaper than a refactor.

`research/additive_perf/simd_proto.cpp` reproduces the hot body (all optional
layers off) over 9 read + 2 write streams and compares a faithful scalar
control against explicit AVX2 at 8 lanes per iteration.

| N | scalar ns/s/p | simd ns/s/p | speedup |
|---|---|---|---|
| 32 | 40.63 | 2.15 | 18.9x |
| 96 | 36.99 | 2.01 | 18.4x |
| 200 | 66.66 | 3.53 | 18.9x |
| 512 | 67.13 | 3.51 | 19.1x |

Outputs agree to 1.25e-6 absolute (2.1e-6 relative), which is the expected
consequence of reordering the accumulation and using FMA.

**Verdict: phase 1 PASSES, by 9x more than the criterion required.**

But 18x is well past the 8-lane ceiling, so part of it was never
vectorization. Two extra rungs were added to find out which part:

| rung | vs scalar | bit-exact? |
|---|---|---|
| scalar + int-cast trunc | 1.40-1.50x | yes |
| + reciprocal instead of divide | 1.58-1.79x | no |
| AVX2, 8 lanes | 18.4-19.1x | no |

The first rung is the story of front 2. The rest of the gap over 8x is FMA
(the engine builds SSE2-baseline, so scalar gets no FMA) plus the per-partial
branches becoming selects.

### The sizing measurement that changes the stage plan

Before building anything on that 18x, a new tool — `tools/ablate_layers.py` —
asked a question the existing ablation harness structurally cannot, because it
profiles the `prof_*` patches which have every optional layer OFF. It zeroes
one layer at a time in a copy of a REAL patch and re-times.

`patches/viola_default.json`, before front 2 landed:

| variant | ms | share of loop |
|---|---|---|
| full | 1387.0 | |
| motion off | 477.6 | **65.6%** |
| bandwidth off | 1294.1 | 6.7% |
| shimmer off | 1373.3 | 1.0% |
| trade / onset off | — | 0 (noise) |
| ALL off | 362.7 | 73.8% |

Two consequences, and the second one is the important one.

The 65.6% became front 2 immediately.

**A layer-free vector fast path reaches only ~26% of this patch's loop cost
(51% after front 2 landed).** The flagship patches — `viola_default` and the
v6 CMA-ES target — run motion + shimmer + onset + bandwidth together, and
`bandwidth` carries a per-partial walk off a **shared** rng. Vectorizing that
changes the order of rng draws, which does not perturb the noise, it *re-rolls*
it. So the configuration the prototype makes 18x faster is precisely the
configuration the patches that matter do not use. Stage 2d is restaged in the
spec accordingly; that is a design change, not a failure, and it was worth
finding for the price of a prototype rather than for the price of a refactor.

## Front 2 — the two libm calls (both landed)

### truncf — commit `e31d936`, 1.6x, bit-exact

`std::truncf` was in the body under a comment asserting it was "a single
instruction where fmodf is a libm call". It is not: `roundss` is SSE4.1, the
engine builds `/O2` SSE2-baseline with no `/arch`, so MSVC emits a **CRT call**
— once per partial per sample. The int round-trip is `cvttss2si` + `cvtsi2ss`
and is bit-identical to `truncf` for every `|x| < 2^31` (here `pfreq` is capped
at CUTOFF one line above, so `pfreq/rate <= 1/3`).

Marginal cost on the 32/200 ladder, binaries alternated, two independent runs:
**41.7 → 26.1 ns/sample/partial (1.60x)**, reproduced at 1.55x. Roughly
500 → 800 partials/core real-time. `null_test_additive.py`: **14/14
byte-identical**.

### fast_exp2 — commit `8396d3a`, 1.7x on motion patches

The 65.6% above was essentially one `std::exp2` in the motion path — another
CRT call, once per partial per sample. `core/fast_math.h` gains `fast_exp2`:
split `x = k + f`, degree-6 minimax on `2^f` over `[-0.5, 0.5]`, `2^k` applied
exactly through the IEEE exponent field. Max relative error **1.9e-9** as
fitted and **1.04e-7 = 0.88 float32 eps** evaluated in float32 — at the
rounding limit of the type, not a coarser approximation. Coefficients from
`research/additive_perf/fit_exp2.py` (IRLS, 400k-point grid), same method as
the `fast_sin_turns` fit.

Measured, alternated, two runs:

| patch | run A | run B |
|---|---|---|
| v6_cmaes_best | 1.72x | 1.74x |
| viola_default | 1.66x | 1.49x |
| no-motion patches | ~1.0x | ~1.0x (noise both directions) |

`viola_default` pre-render 1387 → 781 ms. Motion's share of the loop fell
from 65.6% to 45.4%.

## The one thing that needs your ears — and a real fragility behind it

Residual vs the previous binary is **1 LSB peak / -111 dBFS RMS on 13 of the
15** null-test patches. The exception is `v6_cmaes_best`: -11.7 dBFS peak, 46%
of samples differing. That is not an accuracy problem, and I bisected it rather
than guessing:

| variant | residual |
|---|---|
| as-is | -11.7 dBFS, 46.0% of samples |
| **bandwidth off** | **-90.3 dBFS, 0.5%, 1 LSB** |
| motion off | byte-identical |
| shimmer off / onset off | 1 LSB |

The cutoff gate — `if (pfreq > CUTOFF) return NaN` — sits **before** the
bandwidth block. A 1-ulp change in `pfreq` can flip a partial across that gate;
a flipped partial skips its shared-rng draw, and from then on its noise
realization is a different roll entirely. Pre-existing fragility, newly
exposed, and it has a consequence beyond this commit: **it makes the CMA-ES
objective discontinuous**, since a last-bit parameter change can re-roll the
noise a candidate is scored on. Both questions queued in REVIEW (1 listen,
1 read); A/B pair rendered to `renders/exp2_ab/`.

## Front 3 — the sweep, and two anti-results

Having found the same bug twice by accident, I swept the engine headers for
libm calls reachable from per-sample code. One real candidate came out:
`Formant::get_gain`, two `std::pow` calls, running per in-band partial per
sample times the formants in the spectrum — and all 579 formant instances in
the vowel families use `power: 2`, so a bit-exact `t*t` path was available.

Written, null-tested 14/14, measured — **and it buys nothing**: 1.01x on
`liar_220`, 1.00x on `oo_ee_110` (72 partials at f0 110/220, the worst case in
the library), noise elsewhere. Reverted, with the measurement left as a comment
at the call site so the next pass does not repeat it (commit `682e386`). The
`contains()` gate one line above is why: only in-band partials ever reach it,
and they are a small minority.

The other anti-result, recorded inline in `partials.h`: replacing `pfreq /
rate_` with a multiply by a cached `1/rate_` measured **1.10x in the prototype
and 0.89x in the engine** (marginal 25.0 → 29.6 ns/sample/partial at 200
partials). It also costs bit-exactness. Rejected on both counts.

That makes four dead optimization theories on this loop across runs 12-14
(branchless sin, 4x unroll, reciprocal, formant pow) against three live wins
(batching + caching, fast sin, and now trunc + exp2). The pattern holds: on
this loop, hypotheses are cheap and usually wrong, and the ablation harness is
worth more than the intuition.
