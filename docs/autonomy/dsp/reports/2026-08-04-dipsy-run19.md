## Front 1 — FMSource `phase` was dead; now it is true PM (backlog 3c2) — commit fbbcb44

`FMSource` advertised `phase` in `param_descriptors()` and `WaveSource::set_param`
routed it to `phase_`, so the loader accepted it. But `compute_wave_value()` ran
private `carrierPhase_`/`modPhase_` accumulators and never read `phase_` — nor
`currPos_`, which every other `WaveSource` subclass uses. Proven byte-exactly
BEFORE touching anything, by rendering each phase-wired patch against a twin with
the `phase` param deleted outright:

    t1_06_phase_lfo         86e2d1b9...  (+-1 cycle @ 1.7 Hz on phase)
    _ctrl_t1_06_phase_lfo   86e2d1b9...  (phase DELETED)          <- identical
    t1_07_phase_audiorate   3fa49bbb...  (+-0.5 cycle @ 220 Hz)
    _ctrl_t1_07_...         3fa49bbb...  (phase DELETED)          <- identical

So the two "PM" cells in the run-12 matrix batch were plain FM. Any verdict given
on them was a verdict on the wrong signal.

**Fix**: `phase` is applied as a carrier-side OFFSET. That matches the base-class
contract rather than inventing one — `WaveSource::next()` keeps
`currPos_ = phase_initial + sum(incr) + sum(phase_i - phase_{i-1})`, which
telescopes to `phase_current + sum(incr)`, i.e. an offset, not an integrated
delta. It is never fed back into `carrierPhase_`; doing so would integrate the
modulator a second time and turn PM back into FM.

**Verification** — `tools/null_test_fm.py` asserts a partition, not a sweep:

    unwired phase : 131 identical, 0 DIFFER (expect 0)
    wired phase   : 4 differ (expect all), 0 identical (expect 0)
    PASS

131 bit-identical because `double(x) + 0.0` is exact for every finite float.
New `research/fm_alias/measure_pm.py` shows the change produces actual sidebands
rather than merely a different file:

    t1_07 audio-rate PM   centroid 428 -> 602 (1.40x), rms bw 1.19x
    t1_06 slow +-1cyc LFO centroid flat, peaks 6 -> 109

Both are correct PM behaviour and they differ for a reason worth stating: a slow
phase sweep is a frequency deviation (`dphi/dt`), so it smears each partial into a
cluster of 1.7 Hz-spaced sidebands without brightening; audio-rate PM at index pi
brightens properly.

**The null test then caught a third patch the fix did NOT resurrect** —
`t3_23_phase_velvet_jumps`, still byte-identical. Two patch-side bugs, not engine
bugs: `RangeSource(min=-1, max=1, normalized=false)` is the identity map and
`VelvetNoiseSource` emits exactly {-1, 0, +1}, so every phase offset was an
INTEGER number of cycles — inert by construction. And it set `"frequency"` on a
source whose params are `density`/`amplitude`. Now `density=20` with +-0.5 cycle
(half-cycle) jumps. Isolated three ways so the engine and patch changes do not
get conflated:

    old patch / OLD engine : 1076f8c3
    old patch / NEW engine : 1076f8c3   <- engine fix alone moves nothing
    NEW patch / NEW engine : a6436672   <- fix is live once the patch can express it

## Front 2 — the loader silently ignores unknown params (62 found) — commit e33c59e

t3_23's dead `"frequency"` key is not a one-off, it is a hole in the loader.
`wire_params_generic` iterates the engine's DESCRIPTORS and picks matching JSON
keys; **any key matching no descriptor is dropped without a word**. A typo, or a
param borrowed from the wrong source type, renders exactly as if it had never
been written, and the patch looks fine.

New `mforce_cli --dump-descriptors` emits all 71 registered types' accepted keys
as JSON, so `tools/lint_patches.py` checks patches against the engine's own truth
instead of a hand-copied list that drifts. The one list it owns is `SPECIAL_KEYS`
(keys consumed by hand-written branches in `patch_loader.cpp`), allow-listed
globally so the tool under-reports rather than cries wolf. `--selftest` verifies
it flags a known-bad key and stays quiet on the good twin.

**First run: 62 silently-ignored params across 27 files.** Fixed the 7 that are
live in your FM review batch: `WanderNoiseSource`'s rate param is `speed`, not
`frequency`, so `n3` in every `t2_11_all_noise_wander` cell had been running at
the default 1.0 instead of 7.0. All 7 renders now differ from their pre-fix twins
(`renders/wander_fix/`).

**Then the tool cried wolf and I caught it.** Three of those 62 were FALSE
POSITIVES: `RepeatingSource`'s `gap` and `PhasedValueSource`'s `overlap` are
correct JSON, consumed by `JsonConfigurator` lambdas in
`source_registrations.cpp` — a second source of hand-written key handling that
my first `SPECIAL_KEYS` extraction never scanned (I only grepped
`patch_loader.cpp`). Worth spelling out because it is a genuinely confusing
case: `gap` sets a member called `gapDuration`, so the JSON key and the config
descriptor name legitimately differ, and nothing in the descriptor set can tell
you that. Allowlist now extracts from BOTH files, with the exact grep recorded
in the source. A linter that cries wolf is worse than no linter, and this one is
explicitly built to under-report.

## Front 3 — two param gaps the linter exposed — commit TBD

Both surfaced by front 2's tool rather than guessed at.

**(a) The noise family had no `amplitude` at all.** `WhiteNoiseSource` and
`PinkNoiseSource` exposed zero params; `BlueNoiseSource`/`VioletNoiseSource`
carried a comment claiming "no modulatable params — spectral shape is fixed by
definition", which conflates shape with level. Every other generator
(`Red`, `Velvet`, `Wander`) has `amplitude`. So the only way to set the level of
white or pink noise was an extra multiplier node, and `mux_noise_test`'s attempt
to set it directly was silently dropped. All four now take `amplitude`, default
1.0.

**(b) The `adsr` preset could not express stage jitter.** `Envelope::make_adsr`
takes six randomization-range args (`attackMin/Max`, `decayMin/Max`,
`releaseMin/Max`); the loader called the 5-arg form and dropped all six on the
floor. Now passed through, with defaults set to `make_adsr`'s own.

**Bit-exactness** — every edit multiplies by exactly 1.0f or preserves the
existing default, so patches that do not use the new keys must be unchanged.
Verified rather than argued, on a 334-patch A/B set (every patch using one of the
four noise types, plus every patch with an `adsr` preset), rendered with the
pre-change and post-change engines via new `tools/ab_render_set.py`:

    compared 327 patches present in both arms
      identical : 327
      DIFFER    : 0

Honest caveat: 7 of the 334 are in neither arm because **the CLI cannot render
them at all** — CombineTest, ks_morph_{flute,horn,saw}_test and
mux_{noise,rednoise,sine}_test all fail with `ERROR: Only StereoMixer output
supported`. That is pre-existing and unrelated to this change (same species as
the run-8 algev conversion), but it matters here because `mux_noise_test` is
precisely the patch that SHOULD have moved — it wires `WhiteNoiseSource`'s
amplitude to an envelope. So the A/B proves "nothing regressed"; it does not
prove the new param works. Backlogged as item 15.

That second half is proved separately by `tools/test_noise_amplitude.py`, which
builds its own patches and asserts the param is real AND linear:

    type                        amp        rms      ratio  verdict
    WhiteNoiseSource           0.50   0.204124      0.500       ok
    WhiteNoiseSource           0.25   0.102055      0.250       ok
    PinkNoiseSource            0.50   0.040809      0.500       ok
    BlueNoiseSource            0.50   0.019380      0.500       ok
    VioletNoiseSource          0.50   0.143965      0.500       ok

(amp=1.0 also returns ratio 1.000 against the no-amplitude default on all four,

A node-level scan first established the blast radius honestly: 375 `adsr` Envelope
nodes exist and **0** of them set any range key, so (b) changes no existing patch
— it is pure new capability. (A file-level grep had said 106; that was a false
positive from `attackMax` on separate `ar` nodes, which already worked.)

## Front 4 — 6 of the 7 unrenderable patches revived (backlog 15) — commit 6fc128b

Front 3's A/B turned up 7 patches the CLI cannot render at all while they work
in the UI — the same mismatch class as the run-8 algev conversion. They turned
out to be **three distinct bugs**, which is why one fix did not clear them:

1. **A bare mono source as `graph.output` was a hard error.** The instrument
   path has auto-wrapped a bare output in a unity channel all along; the
   standard path just refused. Now they agree. I used unity volume + centre pan
   to match the instrument path exactly rather than invent a second convention
   — which does mean it inherits the -3dB equal-power centre pan that is
   backlog 3d. Revives `mux_{noise,rednoise,sine}_test`.
2. **`wire_params_generic` threw on any STRING in a pin or param slot.** But a
   string there is *always* a legacy enum consumed by a hand-written branch
   further down. `WavetableSource`'s `"evolution": "target"` is also an INPUT
   descriptor (for the newer ref-wired form), so the generic loop killed the
   patch before its own special case could run. Strings now skipped; other junk
   still throws so genuine mistakes stay loud. Revives
   `ks_morph_{flute,horn,saw}_test`.
3. **`CombinedSource` read `operation` as a string only**, so legacy patches
   writing the C# enum ordinal died on a raw `json type_error`. Both forms now
   accepted.

`CombineTest.json` still does not render, deliberately. It says
`"operation": 3`, and no current `CombineOp` matches (0=add, 1=multiply,
2=fade). Defaulting it to Add would render the patch while performing an
operation nobody asked for — the exact failure mode this entire run has been
pulling out of the loader — so it now fails with
`ordinal 3 has no equivalent (0=add, 1=multiply, 2=fade)` instead. One word
from Matt settles it (REVIEW 10); I am not guessing at a legacy enum.

All three changes touch only paths that previously THREW, so no working patch
can move. Verified rather than argued: 73/73 byte-identical against the stored
A/B arm, with exactly 6 patches present only in the new arm — the 6 revived.
