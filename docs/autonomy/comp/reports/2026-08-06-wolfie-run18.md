## Front 1 — #13 section-level key is authorable

### The defect, both halves

`sections[].keyName` was silently ignored: `PieceTemplate::SectionTemplate`
had no such field, so the parser dropped it without a word and the piece
rendered in the piece key.

Reading the code turned up a **second half nobody had written down**.
`setup_piece_` computed the section scale as
`Scale::get(tmpl.keyName, sd.scaleOverride)` — the section's `scaleOverride`
was realized at the **piece** tonic. A section could therefore change its
scale TYPE but had no way at all to state its TONIC. That is the same hole
`keyName` was reaching for, approached from the other side.

### The decision

The backlog framed it either/or: desugar to a beat-0 `keyContext`, or reject
loudly. **Desugar** — rejecting removes the silent failure but leaves the
author writing a four-line `keyContexts` array to say the most ordinary thing
there is, and there is already precedent one level up (`PieceTemplate.keyName`
+ `scaleName` desugar into `piece.key`).

Two things throw, because they are mistakes rather than shorthand:

```
conflict   rc=1  ERROR: Section 'S1': keyName 'G' conflicts with a keyContext at beat
                 0.000000 — state the key one way or the other (drop keyName, or move
                 the context off beat 0)
garbage    rc=1  ERROR: Unknown PitchDef: H
```

The desugar happens at **compose time**, not parse time. Had `from_json`
expanded it, `to_json` would write both forms and re-reading the engine's own
output would trip the beat-0 conflict throw against itself. Parse stores,
serialize writes back, template round-trips — which is also what makes
`--lint-template` stop reporting it.

`keyName` accepts a bare tonic (`"G"`, type from `scaleOverride`/`scaleName`)
or a full key name (`"G Minor"`). `keyName` + a LATER `keyContext` is legal
and useful, and both were verified rather than assumed:

```
later_ctx  S1: 8:C 9:F# 10:B 11:C 12:B 14:B     <- G major, then D major from section beat 4
full_name  S1: 8:C 9:F 10:A# 11:C 12:C 14:C     <- G minor: F natural and B-flat
```

### Verification

**Null test — 38/38 WAVs byte-identical.** Not argued from the code being a
textual no-op when `keyName` is empty; measured. I saved the three edited
headers, `git checkout`-ed them, rebuilt `mforce_cli`, rendered every one of
the 38 renderable templates in `patches/`, restored, rebuilt, and compared
sha256. Zero differ. (Which is the expected result: a repo-wide JSON scan
found **no** template in `patches/` sets `sections[].keyName` — the only file
in the repo that ever did is run 13's own probe.)

**Lint sweep** — 38 templates + the probe. The probe now reports **zero
findings**, i.e. `sections[].keyName` survives the round trip. The other 27
templates' findings are unchanged and pre-existing (`shapeDirection = 1` and
friends, the known type-default noise; the `chordProgression: array -> object`
FORM findings are the accepted dual authoring form).

**Build** — `mforce_cli` and `mforce_ui` both built in this cycle;
`mforce_ui --stamp` exits 0, `stale : no`. Worth recording *why* the UI did
not relink: neither `mforce_ui` (390 dep files) nor `mforce_engine` (227)
compiles `composer.h`, `templates.h` or `templates_json.h` — zero hits in
either CL.read tlog. Only `tools/mforce_cli/main.cpp` does. So the UI
provably does not depend on this change, and the stale guard agrees.

### What it does NOT do — measured, not asserted

## Front 2 — #18 passage endings land on the grid

### Reproduced, then sharpened

Run 17 reported 37 of 74. At HEAD, on the 21-passage batch (23 render files):

```
ends on integer beat:  6/23
ends on a 4/4 barline:  5/23
```

**Two of those 23 were stale.** `pedal_buildup_3_1.json` and
`sequence_passage_3_1.json` are dated 08-01 07:12 — leftovers from an old
`--takes 4` run that a `--takes 3` batch never overwrites and every sweep
since has silently included. Deleted. On fresh files only the honest
pre-change figure is **5/21 on the beat**. Worth knowing for run 17's 37/74
too: that directory accumulates.

### Cause

`sample_cell` draws a pulse per candidate — deliberately, because without that
draw two takes at different seeds rendered byte-identical — and the cell is
`round(beats / pulse)` notes of that pulse. Nothing downstream reconciled the
accumulated total with the beat grid. The phrase path has done exactly that
since run 13; the passage path never got the equivalent.

### Fix, and where it goes

`passage_anchors::grid_complete(Passage&, grid)`, applied once centrally in
`Composer::compose_passage` — the single point every passage strategy returns
through, so a strategy written tomorrow gets it for free. **Nearest** multiple,
not ceiling: run 17 measured ceiling-to-the-next-barline as the dominant term
in the phrase path's own ending overshoot. Guards: no-op under 1e-3, and a
shrink that would take the final note below 0.25 beat rounds up instead.

`PassageTemplate::endGrid` — 1.0 (integer beat, default), 4.0 (4/4 barline),
0 (off). Not a compat shim: ending off-grid is a real musical choice (a pickup,
an elided handoff), and the knob is what makes it expressible.

### The second mechanism, found by measuring rather than assuming

That got 21/23 — and the two stragglers were the interesting part.
`pedal_buildup_3` was one of the stale files. `wandering_24x` was real:

```
composed:  101 units, sumDur 49.0     <- grid completion WORKED, cleanly
section:    48.0 beats
realized:   99 notes, ending at 48.042
```

The passage was composed LONGER than its section. Realization stops *starting*
notes at the boundary, but the last one to get in kept its full duration and
overhung — so quantizing the final unit could never help, because that unit was
never realized. Notes are now clamped to the section end, which makes any
truncated passage end exactly ON the boundary. After the clamp: **21/21**.

### Three arms, rendered

`renders/passage_end_grid/{off,beat,bar}` — same 21 passages, `endGrid` the
only difference:

| arm | endGrid | on integer beat | on 4/4 barline |
|---|---|---|---|
| `off` | 0 | 6/21 | 5/21 |
| `beat` | 1.0 (default) | **21/21** | 8/21 |
| `bar` | 4.0 | **21/21** | **21/21** |

`off` reads 6/21 against the 5/21 pre-change baseline, and the extra one is
exactly `wandering_24x` — the clamp is deliberately NOT gated on `endGrid`,
because a note ringing past its section end is a bug in any arm.

Beat vs bar as the default is a taste call, not a metric one — **REVIEW 17**.

## Front 3 — #19 the empty render

### Half of it does not reproduce

`wandering_24x` renders **99 notes** at HEAD, not 0. Run 17 could not test this
(no CLI available that run). Whatever produced the empty render is gone; there
is nothing left to fix on that side.

### The other half was a real design question, and the flag was not enough

Run 17 added a `scorable` flag so a batch could SEE an empty render. #19 asked
whether `score()` should refuse instead. It should. A flag is advisory, and
every aggregator that forgets to read it averages the placeholder in as though
it were a score — which is exactly how 0.407 got reported for zero notes.

A composite over 0 notes is not LOW, it is UNDEFINED. `composite` is now `None`
below the 4-note threshold, so arithmetic on it raises instead of quietly
succeeding:

```
empty (0 notes)  scorable=0 n_notes=0   composite=None
one note         scorable=0 n_notes=1   composite=None
three notes      scorable=0 n_notes=3   composite=None
four notes       scorable=1 n_notes=4   composite=0.648
eight notes      scorable=1 n_notes=8   composite=0.842
```

I checked this was safe before doing it rather than after: **no caller feeds
`score()` fewer than 4 notes.** `figure_transforms` samples at `kmin=5`; the
phrase and passage drivers score whole renders. I had assumed figure-level
scoring would break on 2-3-note figures and that turned out to be wrong.

Five aggregation sites in the three batch drivers now filter on `scorable`
(2 in `bake_off.py`, 3 in `markov_phrase.py`) — those can legitimately meet an
empty render. `figure_transforms` deliberately does **not** filter: it scores
figures it constructed itself, so a sub-4-note figure there is a bug that
deserves a traceback, not a silent skip.

Verified: `figure_transforms` plausibility table unchanged to the digit
(original 0.674, invert 0.688, retrograde 0.704, …), passage batch runs clean
at 21/21 rows with all composites numeric, all three files parse.
