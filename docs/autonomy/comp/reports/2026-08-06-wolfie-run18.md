## Front 1 — #13 section-level key is authorable

### The defect, both halves

`sections[].keyName` was silently ignored: `PieceTemplate::SectionTemplate`
had no such field, so the parser dropped it without a word and the piece
rendered in the piece key.

Reading the code turned up a **second half nobody had written down**.
`setup_piece_` computed the section scale as
`Scale::get(tmpl.keyName, sd.scaleOverride)` — the section's `scaleOverride`
was realized at the **piece** tonic. A section could therefore change its
scale TYPE but had no way at all to state its TONIC. That is the same hole
`keyName` was reaching for, approached from the other side.

### The decision

The backlog framed it either/or: desugar to a beat-0 `keyContext`, or reject
loudly. **Desugar** — rejecting removes the silent failure but leaves the
author writing a four-line `keyContexts` array to say the most ordinary thing
there is, and there is already precedent one level up (`PieceTemplate.keyName`
+ `scaleName` desugar into `piece.key`).

Two things throw, because they are mistakes rather than shorthand:

```
conflict   rc=1  ERROR: Section 'S1': keyName 'G' conflicts with a keyContext at beat
                 0.000000 — state the key one way or the other (drop keyName, or move
                 the context off beat 0)
garbage    rc=1  ERROR: Unknown PitchDef: H
```

The desugar happens at **compose time**, not parse time. Had `from_json`
expanded it, `to_json` would write both forms and re-reading the engine's own
output would trip the beat-0 conflict throw against itself. Parse stores,
serialize writes back, template round-trips — which is also what makes
`--lint-template` stop reporting it.

`keyName` accepts a bare tonic (`"G"`, type from `scaleOverride`/`scaleName`)
or a full key name (`"G Minor"`). `keyName` + a LATER `keyContext` is legal
and useful, and both were verified rather than assumed:

```
later_ctx  S1: 8:C 9:F# 10:B 11:C 12:B 14:B     <- G major, then D major from section beat 4
full_name  S1: 8:C 9:F 10:A# 11:C 12:C 14:C     <- G minor: F natural and B-flat
```

### Verification

**Null test — 38/38 WAVs byte-identical.** Not argued from the code being a
textual no-op when `keyName` is empty; measured. I saved the three edited
headers, `git checkout`-ed them, rebuilt `mforce_cli`, rendered every one of
the 38 renderable templates in `patches/`, restored, rebuilt, and compared
sha256. Zero differ. (Which is the expected result: a repo-wide JSON scan
found **no** template in `patches/` sets `sections[].keyName` — the only file
in the repo that ever did is run 13's own probe.)

**Lint sweep** — 38 templates + the probe. The probe now reports **zero
findings**, i.e. `sections[].keyName` survives the round trip. The other 27
templates' findings are unchanged and pre-existing (`shapeDirection = 1` and
friends, the known type-default noise; the `chordProgression: array -> object`
FORM findings are the accepted dual authoring form).

**Build** — `mforce_cli` and `mforce_ui` both built in this cycle;
`mforce_ui --stamp` exits 0, `stale : no`. Worth recording *why* the UI did
not relink: neither `mforce_ui` (390 dep files) nor `mforce_engine` (227)
compiles `composer.h`, `templates.h` or `templates_json.h` — zero hits in
either CL.read tlog. Only `tools/mforce_cli/main.cpp` does. So the UI
provably does not depend on this change, and the stale guard agrees.

### What it does NOT do — measured, not asserted

Run 13's carried caveat reproduces exactly. A section key changes which
**accidentals** appear; it does **not** move the tonic. Rendering the run-13
probe (sections C / G / D) before and after:

```
beat   before   after      sec
  9.0   F        F#         S1   <-- CHANGED
 17.0   F        F#         S2   <-- CHANGED
 19.0   C        C#         S2   <-- CHANGED
 20.0   C        C#         S2   <-- CHANGED
 22.0   C        C#         S2   <-- CHANGED

sections BEFORE: S0 C Major  S1 C Major  S2 C Major
sections AFTER : S0 C Major  S1 G Major  S2 D Major
```

Every section still starts on C3. In D major that start is not even a scale
tone, so the cursor snaps to C# — visible at beats 20 and 22. The three-arm
A/B in `renders/section_key/` shows what the alternative sounds like:

| arm | S1 | S2 |
|---|---|---|
| `control` (no section keys) | C3 F3 B3 C4 C3 C3 | C3 F3 B3 C4 C3 C3 |
| `accidentals_only` (what landed) | C3 **F#3** B3 C4 C3 C3 | C3 **F#3** B3 **C#4 C#3 C#3** |
| `transposed` (+ startingPitch offset) | **G3 C4 F#4 G4 G3 G3** | **D4 G4 C#5 D5 D4 D4** |

Three distinct renders by sha256. **REVIEW 16** — whether `keyName` should
imply the transposition is a semantics call, not something to iterate on
blind.
